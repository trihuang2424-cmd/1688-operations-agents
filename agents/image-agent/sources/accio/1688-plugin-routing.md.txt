# 1688 商家工具集：平台调用约定

本插件启用时，按下文处理其业务及图像任务；其他插件的业务流程不受影响。业务流程、选项、取数口径继续以对应 SKILL.md 为准。本文件规定的是在 AW 中如何执行这些交互，不是额外的业务确认步骤。

## 图像任务：ImageAgent 与 AW 通用生图共存

ImageAgent 是本插件提供的图像能力，不是某个智能体的专属能力。启用本插件只表示该能力可用，不代表所有图片任务都交给 ImageAgent；无需切换智能体。按用户任务类型和业务上下文选择工具，不根据智能体名称设置不同的路由规则。先按任务类型确定路径，再判断是否具备执行条件；不要先找一个能出图的工具再倒推业务归属。

### 先确定业务路径，再检查能力并执行

在读取任何生图 Skill、搜索生图 MCP 或调用生图工具之前，先按以下规则选择 ImageAgent 或 AW。通用 `image-prompt-guide` 虽然也描述商品图、白底图和换背景，但它只指导已经选定 AW 路径的任务，不决定业务路由，不能覆盖本插件的规则。

用户明确要求 ImageAgent，或任务属于以下任一 1688 商品图像场景时，路由到 ImageAgent：主图、副图、轮播图、详情图、工厂实力图、模特替换、换背景。其他涉及 1688 商品图像的生图/编辑/选择/应用操作（对已有图片抠图、去背景制作白底，以及扩图除外）同样路由到 ImageAgent。从零生成 1688 商品图时，白色背景只是画面要求，不属于上述抠白底例外，仍按 1688 商品图像任务路由。执行时先调用 `read_image_agent_execution_rules` 读取规约，再在后续工具调用批次派发 `image_agent_run`，跳过 `image-prompt-guide` 与通用 `image_edit` 编排。ImageAgent 可接收授权有效店铺的 `loginIdList` 并使用其数据。派发图像任务时，若任务中已包含商品 ID，须在任务说明中告知 ImageAgent 该商品已选定，无需再引导用户人工选择商品。

其他操作默认路由到基座能力，不调用 ImageAgent：与 1688 商品图像无关的通用创意生图、修图（包括已选店铺下的同类诉求），以及仅提及 1688 但不涉及商品图像生图/编辑/选择/应用的任务，以及对已有图片抠图、去背景制作白底，以及扩图，均沿用原路由。用户明确指定 `image_generate` 或 `image_edit` 时走通用路径；工具咨询、比较或要求排除 ImageAgent 时进入说明模式；图像执行以用户明确授权为起点。指定工具缺失或调用受限时报告状态并等待决定，切换其他可能计费的工具须先获得同意；同一目标失败后暂停执行，用户再次明确要求时重新派发，商品图片应用仍受既定重试限制。

ImageAgent 支持通用生图、编辑、提示词优化，以及商品图诊断/增强、背景替换、精准编辑、换模特/试穿、多图合成、风格复刻、批量图和主图/副图/详情图/套图/工厂实力图。通用图像诉求保持通用任务属性；纯 OCR、识别、检测超出其通用能力边界；肖像编辑须同时满足合法合规、权利清晰和用户授权。

业务归属结合本轮要求、上传图片、历史上下文及会话勾选店铺判断，不要求用户每轮重复写“1688”，也不以是否读取店铺数据作为分流条件。仅开启插件或泛称“商品图片”不单独证明属于 1688；明确属于其他平台的任务按对应能力处理。前文已明确为 1688 商品的续改沿用上述路由，但上述抠白底、扩图及用户明确指定工具仍按上述例外处理。按语义判断，不把网页轮播组件、`1688×1688` 尺寸或画面文字“1688”当作 1688 商品业务；用户明确切换到无关创作时不继承旧商品任务的路由。

### 授权与派发

- 应走 ImageAgent 的任务须有有效1688店铺授权。以平台提供的当前授权状态和工具可用性为准，不能由“已开启插件”推断“已授权”。平台提示未授权时，引导用户前往「1688生意助手」插件详情页的「应用授权」连接1688店铺，并在会话中勾选有效店铺；已有授权但平台提示失效或缺少必要身份时，按提示重新授权。不要因未授权静默切换到 AW；普通生图仍可使用 AW。状态未知时不猜测失败，由 Host 执行期校验。
- 当前连接器上下文提示 `No 1688 store is available in this conversation scope` 时，说明本会话没有可用店铺，可能尚未授权或未勾选。对于已选定 ImageAgent 的任务，应提示用户检查上述应用授权和店铺勾选，完成后继续，并结束本轮派发；不要搜索、读取或调用其他生图 Skill、AW 生图工具或生图 MCP 来替代。不要把无可用店铺直接说成服务故障，也不要声称已拉起授权页面。
- `loginIdList` 由 Host 自动携带当前会话勾选且授权有效店铺的身份；不询问、猜测或手工填写 loginId，也不在派发前强制要求用户只选一家店。业务涉及哪些商品、素材由下游结合任务要求处理。
- 确定走 ImageAgent 后，不先读取 `image-prompt-guide` 或调用通用 `image_edit` 编排。输入齐备时先调用 `read_image_agent_execution_rules`，再在后续工具调用批次使用 `image_agent_run`；具体输入模式、参数、交互、结果交付和重试规则遵循当前执行规约，不在此复制或改写工具协议。
- 编辑或换模特缺少真实原图/授权商品时，按当前规约补齐输入；用户要从店铺选商品时走规约中的商品选择流程。已有选定商品或上一轮图片产物时复用真实引用，不让用户重复选品，不伪造图片或商品标识。
- 已选定 ImageAgent 路径后，如果 `read_image_agent_execution_rules` 或 `image_agent_run` 未出现在当前原生工具列表中，先根据平台授权状态给出上述授权指引；授权状态正常或未知时，如实报告 ImageAgent 入口当前不可用并停止派发，不猜测授权失效。这两个入口不是待搜索的 MCP 工具，不通过 CLI 寻找替代品，不将其他生图服务称为同一服务。此规则也适用于用户没有点名 ImageAgent、由本插件规则选定的任务；只有用户随后明确要求改用其他工具，才重新选择路径。
- 不要把文字方案、调用结束或组件展示当成图片已交付、商品图片已应用，按实际产物与业务回执报告结果。

## AW 通用生图规范

先按上节完成图像工具路由。本节仅适用于确定走 AW 通用生图的图片生成、编辑、套图及批量处理；原生裁剪、缩放、转格式等处理遵循所选 Skill。走 ImageAgent 的任务继续遵循其当前执行规约，不额外套用本节的 Skill 加载、工具参数或交互流程。

本节统一规定 AW 通用生图的范围、授权、澄清和执行条件；具体 Skill 提供场景规则、平台规格、提示词方法和工具映射，不额外增加图片确认步骤。本节中的 `ask_user` 指普通 Agent 交互；已经进入 Workflow 时仍使用下文规定的 Host 交互链路，不在外层重复提问。

### 识别任务，控制范围

- 区分单图、套图、独立批量及咨询/方案请求，遵守用户指定的数量和修改边界。单图仅需用途、主体/来源、修改项、保留项、尺寸及必要文案；批量明确输入输出对应关系并保留各素材差异；仅套图展开 ImageStory，任何存在依赖的多输出任务都应规划依赖图。商业背景或绑定店铺不自动扩大任务，平台建议不覆盖用户明确要求。参考图任务遵循适用的编辑路线，确定性裁剪、缩放、转格式优先采用原生处理能力。

### 先准备，再判断是否执行

- 按“识别范围 → 加载资料 → 规划与构造提示词 → 最终检查 → 执行”推进。明确的生成、编辑请求即授权；仅咨询、评审、要方案或要求先审批时，不生成。复用已确认信息和可靠默认值，仅对必需素材、关键歧义、冲突、必要事实/文案及授权缺口，通过 `ask_user` 合并提问。后续仅追问新发现且此前无法合理收集的必要问题；解决后保留原授权。

- 执行前检查：范围与数量、修改及保留边界、素材与规范、事实与语言、工具参数、套图及依赖。条件齐备就执行全部授权输出，不再询问或只交方案；发现阻塞可提前询问，无需硬凑完整提示词。新信息出现后，仅更新并复查受影响的输出。能力缺失或不可恢复的失败如实说明。

### 按需加载规范，落实工具参数

- 先根据 Skill 元信息，按目标、保留要求和允许修改范围，为每个输出或子任务选择一个最匹配的主 Skill，再加载选中的正文；专用能力优先，无更匹配的专用 Skill 时，默认使用 `image-prompt-guide`。已选定专用 Skill 时，不再额外加载 `image-prompt-guide` 作为前置步骤。必读正文不能由路由摘要替代。已知独立资料在工具限制内同轮读取，去重并复用仍有效的内容；必要参考齐备后再详细规划，仅补读新增、缺失或变化部分。补读资料或执行独立图片时，不重复启动已完成的整体规划。

- 参数优先采用用户要求，其次采用可靠的平台/Skill 默认值；关键规范缺失、过时或冲突时检索核实。提示词与实际参数须一致；调用 `image_generate` / `image_edit` 时，每次显式传入 `size=宽x高`，优先于 `aspect_ratio`，并遵守分辨率规则，包括 16 倍数约束。

### 保持主体准确，服务图片目的

- 保留主体形状、比例、颜色、材质、纹理、结构、Logo 和原有文字，不臆造不可见细节。局部编辑保持未涉及内容和构图；场景变换可合理调整机位、摆放，保留要求优先于创意变化。

- 每张图突出一个主要目的，主体和核心信息优先于背景装饰，兼顾接触关系、尺度、透视和文字安全区。套图保持身份与风格一致，按用途变化构图，避免机械换背景。文案仅在用户要求或用途适合且平台允许时添加，保持简短、有层次；不自动添加 CTA、无关第三方品牌或人物形象。已提供或授权素材无需例行重复确认权利，只有具体授权疑点构成阻塞时才询问。

### 分别确定语言与事实

- 对话语言遵循用户当前指令，不受参考资料语言影响；混合语言请求的指令语言不明确时，采用该请求的主要语言，无需追问。此规则只决定对话语言。新增或改写的图中文字依次采用：用户明确要求、当前任务已确认语言或逐字使用的最终文案、明确目标平台的可靠默认语言。Amazon、阿里国际站默认英语，1688 默认简体中文。仍无法确定时必须询问，不凭对话、参考图、通用默认值或绑定店铺推断。套图统一确定文字语言，仅语言未解决时合并询问，已明确或有可靠平台默认值时不再确认；保留逐图及多语言例外，并在提示词中绑定各文字元素的内容和语言。无文字或原文不变时无需询问。

- 商品事实分为：**A 已由用户提供/确认或用户提供的官方资料支持；B 推测；C 未知；D 已知虚假、伪造或不允许使用。** 仅 A 可进入提示词；可选 B/C 省略，必需时询问；D 排除。会话及店铺记录沿用原始事实来源，不因写入记录而将推测或未知信息升级为 A 级。来源与内容合规分别判断，数字、排名、认证等不因形式自动获准或禁用。无具体矛盾时不重复索证；构图、配色、光线和合理受众假设属于设计决策，不得据此推导商品性能。

- **认证标识约束：** UL、FPA 等国际认证相关标识，只有用户明确提供该商品对应的认证信息/标识，或已向用户确认该商品具备相应认证，才可在适用内容规则内按需加入图像。不得依据品类、外观、目标市场、竞品或模板推断认证，也不得自行添加认证 Logo、徽章、证书编号或“已认证”等背书文字。缺少依据的可选标识直接省略；用户明确要求添加但未提供对应信息时，合并询问确认。保留用户原始素材中的已有标识不代表可以扩展为其他认证或新增背书。

### 紧凑规划套图，按真实依赖并行

- 根据用户、会话和适用店铺信息确定受众、用途及决策顺序；缺失时采用合理设计假设，只有不同理解会显著改变结果且无安全默认选择时才询问。套图每张图内部记录：`序号｜受众问题/角色｜图片任务｜构图｜主张（可选）｜视觉证据｜辅助信息｜禁用项｜依赖`。白底、无文案和保留型图片不强加卖点；未知的期望行动直接省略，不为 CTA 额外提问。

- 统一主体、配色、光线、字体和语言；每张图的提示词须独立携带共享风格、本图任务与构图、保留项、允许使用的事实/文案及禁用项。套图默认共用已确定的平台尺寸，明确例外除外。仅实际“上游输出作为下游输入”构成依赖；共用原图、风格或编号不构成依赖。可由已授权上游任务产生的素材属于执行依赖，不作为向用户提问的阻塞项。就绪的独立任务在工具限制内同轮发起，仅因真实依赖、用户顺序或工具限制分批。必要中间素材生成一次，下游使用真实返回素材，不扩大最终数量。任务跟踪按需使用，不造成串行；上游失败只停止依赖项，继续可行的独立任务，保留成功结果，最终按逻辑顺序交付。

- 规划、事实分级及依赖图默认内部完成；仅在用户要求方案、要求审批，或阻塞选择需要比较备选方案时展示。需要用户比较方案时，先展示相关备选方案，再调用 `ask_user`，不得只给出缺少背景的确认问题。

## 展示结果：LOGINID 外壳逐字保留

工具返回里的 `LOGINID_<base64>_LOGINID` 是账号外壳，由前端在展示层解码为明文。向用户输出筛选、明细或客户列表时，无论是转发还是重新组织表格、列表、摘要，都必须逐字保留完整外壳（含 `LOGINID_` 前缀和 `_LOGINID` 后缀）：不要解码、翻译、缩写、截断、打码、重编码或改写，也不要自行补 base64 padding。外壳改动任何一个字符都会让整串解出非法 UTF-8，前端只能原样渲染，用户看到的裸外壳比明文更难认。

`subagents/crm-agent/prompt.md` 已规定外壳在 CLI、计划和 Slot 间原样传递，本节覆盖面向用户的展示与重组，两者口径一致。工具入参不受本节影响：CRM 工具同时接受明文 loginId，传入明文时原样传，不要反向编码成外壳。

## 平台等待与业务策略边界

空结果后的诊断范围、重试次数、业务降级、默认查询范围与任务结束条件由对应 Skill 定义。本插件级适配提示不覆盖这些策略。店铺由平台当前任务上下文管理，收到选店提示时等待真实选择；不能将等待误报成远端服务故障。

通过 `accio-mcp-cli` 调用工具时，默认不在 Python `subprocess.run` 外层增加固定超时：该过程可能正在等待用户选店。PC Host 分开管理人工等待、远端执行超时和任务取消；确有业务执行期限时，应明确说明它的范围，不把默认选店等待误判为服务失败。

## SubAgent 交互卡片透传

SubAgent 返回 `PARENT_SLOT_RELAY_REQUIRED` 信封，表示相关业务草稿已经创建、卡片中的配置已经生成，当前正在等待用户编辑和确认。主 Agent 必须将信封内的 `:::slot[...]` 标记逐字原样复制到面向用户的最终回复中，且该标记独占一行；不得删除、摘要、改写或重新生成 Slot ID，也不得重复创建草稿或重新运行卡片准备工具。

此时只能表述为“草稿已创建、配置已生成、等待编辑确认”，不得表述为“已发送”“已触达”或“执行完成”。最终回复只保留必要的一句状态说明和原始 Slot，不转述信封标签，也不在 Slot 前后补写画像表格、配置明细或模型自行生成的方案。例如：

```text
已创建触达计划草稿，优惠券和话术已经生成。请在下方卡片中编辑并确认；确认前不会发送给客户。

:::slot[SubAgent 返回的完整 opaque ID]
```

## 普通 Skill：使用真实工具并等待

本插件文档中的 metadata.interactions、selectionType、type: card/input、select_erp 等名称描述的是 Newton 的交互意图，不是 AW 工具名，也不是可以直接执行的消息正文协议。

当业务需要用户选择、输入或确认时，调用当前可用的原生 ask_user 工具，等待真实返回后再继续。不要把卡片 JSON 当成正文或代码块输出后结束；仅输出“请选择”不会创建等待请求。用户只是要求解释或展示 JSON 示例时，不要弹卡。

- 选择：使用 mode=form；questions 为数组，每题使用唯一的短 header。字符串 options 转成带 label 和非空 description 的对象；allowMultiple 对应 multiSelect，required=true 对应 allowSkip=false。保留原选项的含义，不猜测答案。
- 单项自由输入：使用 mode=chat 和 question；多项输入：使用 mode=fields、question 和带唯一 id、label 的 fields。具体参数以当前工具 schema 为准，不透传 selectionType/type 等不支持的顶层字段。
- 只有“确认”的业务操作：可以使用 mode=chat 的 question 和 quickReplies（例如 ["确认执行"]）展示确认按钮，取消仍停止该操作，不为凑选项添加新的业务方案。
- 消费实际工具返回；取消、跳过不等于同意。若返回含“其他”标记，按工具返回约定读取用户原文，不将标记作为 ERP 名或业务参数。
- 凭证不回显、不写文件、不输出到日志或命令行。需要安全凭证录入而当前能力不能满足时，说明缺口，不降级为普通聊天明文索取。
- 交互无法用当前工具表达时，说明缺少什么；不要声称已显示卡片或已完成授权。
- 普通 Skill 的 `open_tab` 描述仅表示导航意图，输出真实可点击链接并请用户点击；不输出裸协议 JSON，不声称已经自动打开。Workflow 内继续走 Host 的 openTab 能力。

例如“选择 ERP”的原始 options 为 ["聚水潭", "吉客云"]、allowMultiple=false、required=true 时，应发起以下 ask_user 工具调用，而不是把下列 JSON 发给用户：

```json
{
  "mode": "form",
  "questions": [{
    "header": "选择 ERP",
    "question": "本次库存分析要使用哪个 ERP？",
    "options": [
      {"label": "聚水潭", "description": "使用聚水潭的数据"},
      {"label": "吉客云", "description": "使用吉客云的数据"}
    ],
    "multiSelect": false,
    "allowSkip": false
  }]
}
```

拿到答案后按 Skill 对应路径继续。用户已明确选择时直接使用，不重复询问。用户未选择时，不默认选择 ERP、不发起业务取数。

## Workflow：保留 Host 的交互链路

已经进入 Workflow 脚本时，继续使用 showInteraction，由平台 Host 映射、等待并将答案交回脚本。不要在外层重复发起 ask_user，也不要改成打印 JSON。此规则不要求修改每个 workflow.js，也不替代 workflow 工具的调用合同。

## Workflow 与普通 Skill 的职责

- 插件内的 workflow/*.js 由 PC 按静态 meta 自动发现；调用平台 workflow 工具，action=run，并指定 plugin_id=1688-seller-assistant、workflow_id 和 arguments。不要使用旧工具名 workflow_run，不要另建审批表或让模型用 Bash 执行 workflow.js。
- 自然语言业务请求放在 arguments.request，其他确定性参数放在 arguments；Host 保留完整 params.input，并兼容旧 args。不要把全部业务参数改写成一段猜测性摘要。先读对应 Skill 选择正确入口；一个 Skill 可包含多个 Workflow，调用的是 meta.name，不是目录名。
- jky-auth 负责吉客云状态检查、确保授权和显式换绑，调用方必须分别传 `action=status|ensure|reauthorize`；其中 `status` 只读且不得进入授权交互。1688-item-one-click 负责商品操作；1688-shop-daily-report 负责当前授权店铺日报。其他能力仍遵守各 Skill 的流程，不因为恢复 Workflow 就强制把普通任务全部改成 Workflow。
- 普通 Skill 的业务查询保留 accio-mcp-cli；Python 负责本地计算、文件或规则编排，不恢复自行维护 HTTP 登录态的代码。Workflow 确定性业务节点直接 callTool；已有 Python 聚合链路若内部走 accio-mcp-cli 可继续复用。
- store_ref 只使用平台给出的真实引用，不以店铺显示名/loginId 猜测。Workflow 缺少店铺上下文时由 Host 处理选择与继承；不要把同一条查询重复发给多个店铺试探。
- 店铺引用由 Host 在运行入口选择并通过路由信封继承，业务 callTool 和 Python/CLI 聚合只传业务参数，不逐个注入 store_ref、不设置全局默认；`accio-mcp-cli` 的跨进程调用也由 Host 自动恢复同一选择。
- 普通 Skill 通过 `accio-mcp-cli` 调用第一方 1688 工具时，同样由 Host 在多店铺场景弹出选店卡并等待；不要把 `ALI1688_STORE_REF_REQUIRED` 当成业务失败后自行猜店、枚举店铺或结束流程。用户取消选店才终止本次操作。
- 仅依赖标准库的 Skill 脚本可使用平台 Python 和注入的 `{baseDir}` 绝对定位，例如 `python3 -B "{baseDir}/cli.py" ...`。需要第三方包的脚本使用插件托管环境：`phoenix-plugin-python-run --plugin-id 1688-seller-assistant --script skills/<skill-id>/<脚本路径> -- ...`；`--script` 相对插件根，`{baseDir}` 则是 Skill 根，不得混用。依赖由根 plugin.json 声明，不要求用户手工 pip install，不回退系统解释器或跳过处理步骤；安装失败报告环境准备问题。禁止猜测安装目录或把 Skill 的 cli.py 当作插件根脚本。
- MCP 未注册或调用失败，保留真实错误；是否重试遵循对应 Skill 的策略，不由适配层额外添加或取消重试。
- Workflow 等待用户时不并行发起第二次运行、不由父 Agent 接手重复写操作。当前端无法呈现复杂交互时提示到桌面继续，保留平台已有等待状态，不能宣称已完成。
- completed 只表示脚本运输层结束。Workflow 业务失败必须使用 Newton 原生 `fail(code, message)`，禁止用“失败/终止”字符串正常 return；Host 依据结构化 `businessResult` 判断成功或失败，不扫描自然语言。是否授权成功、写入成功、报告完整，以明确业务结果为准；缺失的数据要说明。需要交付文件时使用实际产物路径和 present_files，不把临时 Worker 路径或“已生成”的文案当成已交付。
