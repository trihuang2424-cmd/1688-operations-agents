# 持续运营与周期衔接

按[加载清单](context-loading.md)读取本次需要的章节。完整周期、经营结论、逐链接执行及重点推广的唯一流程定义在[销售增长工作流](sales-growth-workflow.md)。日常/周/月运行共享同一账本，未创建独立定时任务。

## 持久记录及读取顺序

总控先运行[账本摘要查询](operating-state.md)，领域任务按对象查询；读取当前策略版本、上次结论、执行未知/人工待办/到期事项、相关措施及数据截止，再取得必要新数据。首次业务运行、策略版本变更或约束不清时核对[策略原文](account-strategies/songtai-sales-growth.md)。无账本或历史未核对必须先核对已有报告及回执；空索引不代表从未处理。明确单对象任务只核对本对象相关历史，不以全店尚未建档阻塞其资料/方案工作。

账本位置优先沿用任务指定位置，默认 `reports/operating-state/current.json`。`reviews/actions/focus_products`分别保存诊断、单次措施、长期重点，字段见[模板](templates/sales-growth-records.json)和[账本契约](operating-state.md)；原始证据保留在运行目录。摘要自动派生，不另行手写维护。指标证据保留店铺、实际期间、截止/查询时间、单位/分母/去重、数据源与回补版本。真实数据不混入模拟记录。

询盘问题和请求仅通过[转化状态模块](conversion-state.md)管理，通用账本保存引用。没有原状态时先核对历史，不能另建第二份问题表。公司新要求和人工外部修改须登记，脚本不能自动发现尚未录入的事实。

## 问题与措施分开管理

“链接点击率低”是问题，“更换一版主图验证点击表现”是措施。问题可以持续存在，但已有措施在执行或观察时，不因此再创建一个相同调整。同一问题的多项措施分别保留 action_id、状态、固定基线和复查条件；完成其中一项不覆盖其他措施，也不自动证明问题已解决。任一关联措施结果未知时先核对该措施。

措施状态按实际证据推进：

`待分析 → 方案就绪 → 待执行 → 执行结果核验 → 观察中 → 效果评估 → 已结论`

状态允许明确标记 `受阻`、`执行失败`、`结果未知`、`证据不足` 或 `已取消`；这些不是成功状态。结论说明保持、扩大、调整、恢复、终止或继续收集证据的决定及理由。需要下一项调整时创建关联措施，保留前一项记录，不重写前一次假设或基线。

工具不支持或需要人工的步骤保存 `awaiting_manual_execution` 与具体[人工执行方案](sales-growth-workflow.md#逐链接执行与人工交接)。人工生效回执未取得前不能进入效果观察；生效时间与完整观察区间分别记录。公司长期重点身份由 `focus_id` 管理，单次有限观察由 `action_id` 管理，不把“长期重点”解释为所有措施永久处于观察期。

事实属性纠错可在归属、真实值和写入回读核验后完成正确性验收；不能强制把所有纠错变成经营实验。标题、主图和投流等效果措施需要另行观察。后台回读通过不代表买家页面展示已核查，后者单独记录并遵守根项目授权规则。

## 三种基线各司其职

| 基线 | 用途 | 更新规则 |
|---|---|---|
| 滚动监测基线 | 发现相对近期正常水平的异常，考虑星期、活动和流量结构 | 随可用的完整数据更新，记录窗口和版本 |
| 行动前固定基线 | 评价具体措施后的变化 | 行动前保存原有口径与区间；观察期间不随滚动均值重置，回补数据保留版本和影响说明 |
| 阶段起点与经营目标 | 评价总体经营，避免滚动均值随恶化下移而掩盖问题 | 按阶段管理；改变目标须有依据和版本记录，周检不自动清零 |

基线必须来自真实可追溯数据。没有足够历史数据时标记基线缺口，使用能说明范围的参照，不伪造“改动前七天”。规则预估另存为预估及来源，不能替代实际基线。包括标题曝光预测在内的来源规则及原有条件、数值、免责声明继续保留，不以尚无本店实测而停用；评估时区分其预估与真实观测。

## 何时观察、何时评估

每项效果措施在执行前写明：主要指标、需保护的指标、最早评估时间、样本要求及依据、转化/数据成熟条件、提前干预条件、最晚重新审视时间和负责人。依据对象流量、采购成交周期、数据延迟及已有业务规则确定；不能给所有商品机械套用固定天数或随意的统计阈值。广告来源中的24小时/3天/7天按[已授权修正规则](ad-decision-policy.md)作为可选检查节点，不能据第7天到来直接认定完整效果或决定放量。

- 数据未更新：保留原状态，报告截止时间与延迟，不能把相同历史数据当新发现重复改动。
- 指标仍低且观察未成熟：继续观察，不将其视为措施已失败。记录下一次应检查的条件。
- 样本不足：标为证据不足；到达最晚重新审视时间后决定延长、改变验证设计、保留当前设置或重新诊断原因，不能无限等待，也不能自动判失败。
- 出现新事实、事实错误、明确执行异常或达到既定干预条件：记录依据后处理，可提前结束原观察。仅“仍低于目标”不是新的干预依据。
- 同期标题、主图、价格、投流、活动或库存变化：记录干扰因素。条件允许时采用合适的比较组或平台实验；单纯前后变化不证明因果。
- 相关对象由人工或其他系统修改：按[执行协议](execution-protocol.md)核对差异，重评原措施与待执行方案，不覆盖更新后的事实。

已经在观察的措施保留自己的基线和评估条件。新的周/月策略可以改变其后续决定，但须记录理由、影响及版本，不能静默改成一个更容易达成的成功标准。

## 每日运营

按[工作流](sales-growth-workflow.md#持久记录与交付)检查未完成、人工待办、全部到期措施和重点产品，先处理结果未知和执行异常。投流中的计划交领域按[投流日检](sales-growth-workflow.md#重点推广与每日投流)读取最近完整日及累计；每天检查不等于每天修改。

总控执行 `conversion_monitoring` 轻量检查，按[转化分析协议](../.agents/skills/1688-customer-conversion/references/conversion-analysis.md)选择必要概览；无新信号也须通过现有状态模块 `ingest signals=[]` 扫描历史未结问题及全部措施的到期条件。取询盘/CRM数据前加载对应完整规则，窗口以真实接口为准，不每日扫描全部人员或客户；明确过程超时与成交成熟分开，缺记录不判未跟进。满足触发且无重复时才领取并实际委派专项。

交付实际执行、人工待办、继续观察、到期结论及必要用户事项。数据未更新和样本不足必须说明，保持现状是有效决定。客户维护、报价、接待和触达仍按独立具体任务授权，不因监测自动执行。

## 每周效果检查

按[完整周期与比较基线](sales-growth-workflow.md#完整周期与比较基线)和[经营结论](sales-growth-workflow.md#经营结论)形成全店判断，再排链接队列。检查全部公司重点、到期措施及原转化状态；缺席旧问题不关闭，未到期措施不提前判成败。策略变更保留理由和版本，沿用既有措施基线与复查安排。

## 每月经营复盘

使用 `monthly_review`，按工作流的完整自然月口径复盘全店和公司重点，不能以周报相加或滚动30天替代。到期行动给出结论，未到期继续，人工事项单列；不自动移除公司重点身份或重建另一套转化问题表。

未来开启定时任务时，各周期必须连接同一账本，并协调运行和同对象执行者。当前查询脚本不提供自动调度、远端业务锁或全项目并发安全；中断恢复先核对当前事实，不重放全部过期修改。
