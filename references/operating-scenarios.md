# 当前运营场景与能力调用

迁移日期：2026-10-28（Asia/Shanghai）。本文件合并两份接手资料原第六节的重复场景，保留J01—J21及其业务条件、公司输入和验证要求，统一为当前三个核心角色与按需能力。资料编号A—F、G—I、H类沿用[接手摸底待办](../01-店铺接手摸底待办.md)及[浙江淞泰科技接手资料](../浙江淞泰科技-接手摸底-20261016.md)对应记录，不改变原有公司事实或历史数据。

本文件用于解释如何应用路由，不替代[任务路由真源](../catalog/task-routing.json)、[注册表和旧名映射](../catalog/agent-registry.json)或完整业务规则。业务步骤、数值、前置条件、必要交互与免责声明继续按所选技能及其RULES和来源执行；来源疑问保留待核验，不借场景迁移自行删改。

讨论范围：围绕曝光、访问、询盘、成交及有效做法的延续，梳理不同问题的调用路径。持续改善真实瓶颈有助于提升经营表现，但具体效果仍需结合需求、价格、竞争、履约和成交周期验证，不预设每次修改都能增加成交。

2026-10-30起，本店周期任务先按[销售增长运营流程](sales-growth-workflow.md)完成完整周/月比较和经营结论，再进入下列具体场景。公司重点新品可凭明确要求立项；链接逐一执行或交人工方案，生效后有限观察，到期评估；公司重点产品独立长期跟踪，投流先计划后执行并每日检查。下列场景不另定比较周期，也不把待执行方案当成观察中的措施。

## 6.1 总控如何选择调用路径

处理浙江淞泰科技账号时先读取[本店当前阶段策略](account-strategies/songtai-sales-growth.md)。以下是通用场景，J07/J10/J15/J18/J20/J21等涉及价格或利润的默认路径须按该策略适配；当前主线为新品推广与链接流量/转化，价格固定，成本利润资料不作为推进前置。

根项目当前主Agent是 `operations_director`，直接承担总控，不另启总控子Agent。商品运营为 `product_operations`，流量运营为 `traffic_operations`；下表用中文简称指代这三个负责人。扩展能力归总控协调，任务较重时可实际委派临时专项，但不为每个能力恢复旧岗位。

每日询盘与转化走 `conversion_monitoring` 轻量只读检查；异常、重要新证据或复查到期需要深入分析时走 `conversion_analysis`，有子代理工具必须真实委派同名临时专项。以下场景中的“总控：customer_conversion”是业务归属，不表示总控自行包办这类深析。复用[分析协议](../.agents/skills/1688-customer-conversion/references/conversion-analysis.md)和[状态工具](conversion-state.md)，保留三个核心角色。

1. **先确定需求和状态。** 区分查事实、异常诊断、方案、已授权变更或核验；记录店铺、商品／客户范围、目标、任务模式、策略版本及相关措施。按[周期协议](operating-cycle.md)先读取既有行动、观察状态和上次执行结果。
2. **复用已有证据。** 从第一步A—F、第二步G—I取相关资料；来源、周期和覆盖范围仍适用时复用，只补缺失或过期部分，不要求全部问题填完才推进。缺少集中状态索引不等于从未做过调整。
3. **按任务选择负责人和能力。** 流量问题交流量运营，商品问题交商品运营；全店原因未明由总控用经营分析拆分；询盘、ERP等按需加载对应能力。总控自己的经营摘要、日报和利润子流程直接处理或交一次重数据专项，不为各模块重复启动经营岗位。
4. **按证据推进业务阶段。** 有子代理工具时真实委派商品／流量任务，交接完整适用规则及授权；同一领域内的标题、图片、属性、应用等由该任务切换能力，保留原业务阶段而不创建多重Agent交接。已委派或独立领域会话直接执行本角色，不递归启动自身或总控；宿主不支持命名角色选择时仍真实spawn并在消息中明确入口和规则路径，见[委派约定](delegation.md)。
5. **决定优先级及是否行动。** 综合目标影响、证据充分程度、成本、时效、依赖及现有观察状态排序。数据不足先补证或观察，公司事实缺失交公司负责人；业务条件不具备则暂缓依赖动作。指标仍差但同一措施正在观察时，不凭同一依据每天再改。
6. **执行、核验和效果复盘分阶段记录。** 准备[结构化变更单](execution-protocol.md)，沿用有效授权，只补缺少的具体决定或工具必要确认。执行者核对真实状态，总控协调效果评估；按需独立复核使用 `operations_review`，不新增常驻岗位。

“曝光多／少、转化高／低”需结合本店历史、相似商品、渠道、季节和样本量确定。没有可比基线时先做探索性诊断，不凭统一固定阈值判异常。滚动监测基线用于发现问题，行动前固定基线用于评估措施，阶段起点与目标用于整体复盘；观察期间不每天重置固定基线，每周也不清零既有措施。样本不足保留下一次评估条件和最晚重新审视时间，不无限等待或自动判失败。

ERP通过总控协调的 `erp_inventory` 能力，按实际已接入系统选择聚水潭或吉客云适配，分别保留授权、订阅、字段与粒度条件。公司未接入相应系统时，由仓储／财务／生产负责人提供资料，不假定两个系统都可读取。

所有场景的页面、图片及商品实际展示“实看”均沿用根[实际展示核查规则](../AGENTS.md#实际展示效果核查)：优先承接用户人工核查结果。Agent代为使用网页、浏览器或其他展示核查工具前，必须先说明具体对象、拟用工具、核查内容及可能操作并取得明确同意；仅商品修改授权不包含该核查，不能通过子Agent绕过。没有核查结果时标记待核查，后台字段回读不能替代实际页面证据。已有用户资料和合法取得的后台证据按其实际覆盖范围使用，不虚构“已实看”。

## 6.6 询盘到成交环节的分支

默认日常分析在本节只产生问题、证据、建议与观察条件，不执行客户跟进或提醒。只有另有具体授权时才进入表中的报价、接待配置或触达流程；这些原能力继续保留。没有取得报价、跟进、寄样或线下成交记录是未知，不能当作没有做；新线索未成熟时观察，同一问题沿用既有措施和复查条件，不每天重派。

| 场景 | 当前负责人、能力与首先核实事项 | 条件满足后的业务阶段 | 公司输入与验证重点 |
|---|---|---|---|
| J11｜平台显示询盘多、成交少，但成交链路未核清 | 总控用 `business_analysis` 核对口径，按 `conversion_analysis` 委派专项关联已有可用订单和跟进背景，复用证据 | 可取得时补充站外成交及跟进阶段，缺失则记未知；同队列成熟且真实原因有依据后再选择J12—J16 | H01／H03：同一批客户、站外成交、报价／寄样和成交滞后；未到成交期的线索继续观察 |
| J12｜询盘需求不匹配或质量偏低 | 总控按 `conversion_analysis` 委派询盘与客群分析，抽查许可范围内真实对话并按已确认标准核对客群；需下钻来源时委派流量运营 | 入口需求不匹配回J05／J08；接待判断错误才转J13／J14 | H02有效标准、C06承接边界；询盘质量按可复核样本衡量，不凭客户标签推断 |
| J13｜人工回复慢、答非所问或交接遗漏 | 总控按 `conversion_analysis` 委派人工接待分析，核查实际对话、时段与转人工记录；不自动扫描全员 | 人员排班、培训、分工形成给销售负责人的具体建议；只有独立的AI接待改善需求及相应授权才进入AI接待子流程 | H09排班及站外回复记录；看回复质量、跟进推进和可追踪成交，不能把人工管理问题都交给AI配置 |

| J15｜报价逻辑错误、价格条件不清或客户认为贵 | 总控按 `conversion_analysis` 委派询盘分析核对真实反馈，实际售价／毛利问题用 `business_analysis`／成本利润；需要同款依据时交商品运营竞争比较 | 有具体授权时，已确认AI报价公式问题进入原报价子流程编写、保存和模拟；商品售价／折扣变更由商品运营核实能力及当前销售信息手动边界；人工谈判由销售负责 | E类成本、单位、税运费、数量阶梯；公司先确定规则；保存AI报价草稿不代表上线，也不代表改了商品售价 |
| J16｜有意向客户疑似长期缺少跟进 | 总控按 `conversion_analysis` 委派分析，核查线索阶段、采购周期、记录覆盖及已有联系证据；缺记录不等于没有跟进 | 日常分析记录问题、责任建议与复查条件；另有明确客户运营任务时在原能力中准备计划／话术，仅在已获相应发送授权且渠道支持时触达；微信／电话等交公司人员 | H01／H03／H09；交付聚合问题与有限许可示例、可核实状态及后续条件；没有新证据或到期条件不每日催办、不重复联系 |
| J17｜客户有需求，但库存、交期或定制能力接不住 | 商品运营对照页面承诺并遵守6.2；总控通过 `erp_inventory` 选实际接入系统查询库存／订单，生产负责人确认排期 | 商品运营核查错误展示的可写字段；只有明确补充货源需求才由总控加载 `procurement_research`；补货／排产由公司落实 | D类和H05；ERP查询不等于能写采购或生产任务；核实实际承接能力后再扩大获客 |

## 6.7 持续有效、值得延续或扩大时的分支

| 场景 | 当前负责人、能力与首先核实事项 | 条件满足后的业务阶段 | 公司输入与验证重点 |
|---|---|---|---|
| J18｜商品持续贡献有效询盘或成交 | 总控用 `business_analysis` 汇总，商品运营核实稳定商品贡献；需要判断收益时总控加载同能力的成本利润子流程 | 保留当前有效版本；明确有可比商品时由商品运营准备标题／图片的小范围迁移方案；需要市场扩展才加载 `market_research` | B07、H05／H07：利润、承接能力与战略；验证做法能否迁移，不自动重做畅销品 |
| J19｜老客户有复购机会，或购买间隔异常变长 | 总控：`customer_conversion`／复购分析，对照历史采购、客户阶段与已知采购周期 | 原因和客群明确后在同一能力中准备分层跟进；触达按具体授权执行，商业谈判交销售 | C03、H03／H06：采购周期和反馈；观察真实响应、复购及重复联系情况 |
| J20｜成交增长但利润下降或履约压力增加 | 总控：`business_analysis`／成本利润，核对收入、退款、费用与实际成本；承接问题由 `erp_inventory` 及生产负责人补证 | 总控调整优先级，公司确认价格／供货决策；只有支持且已授权的字段由商品运营处理，不能绕过当前销售信息手动边界 | E类、H05／H07；以可核实利润和履约指标复盘，不能只按GMV继续扩大 |
| J21｜确认有新产品／新品类机会 | 商品运营：`market_research`／机会研究，需要时补可比竞争信息；总控用 `business_analysis`／成本利润核算公司提供的成本 | 公司明确承接方向后，商品运营在同一任务加载 `listing` 准备类目、素材包和草稿，图片用 `image`；确需找货才由总控加载 `procurement_research` | 公司决定产品、MOQ和供货条件；草稿／发布链接不等于新品正式上线，缺少发布接口时交人工完成并核验 |

## 6.8 明确需求可以直接派单

| 用户已经明确的需求 | 最短当前路径 | 限制范围 |
|---|---|---|
| 只看昨日经营情况 | 总控：`business_analysis`／单日 | 交付指定单日数据；只有用户需要或发现相关异常才开启后续任务 |
| 给指定商品比较几个标题，不修改 | 商品运营：`product_optimization`／标题方案 | 复用完整商品事实；不额外全店诊断，不调用效果不明的写接口 |
| 为已确认商品和卖点制作主图 | 商品运营：`image`／既有image-agent | 按用户要求交付方案或实际图片；线上主图应用是另一个明确动作；既有图片不主动再spawn规则保留 |
| 已确定商品、字段和新值，要求应用 | 商品运营：`product_optimization`／共用执行协议 | 核对事实、已有措施、权限及工具前置，执行与回读；不发散完整策划 |
| 查看当前AI报价规则 | 总控：`customer_conversion`／报价只读子流程 | 查询已有生效方案，不为查看自动创建草稿 |
| 检查询盘和转化是否出现新问题 | 总控：`conversion_monitoring`；需要深析时实际委派 `conversion_analysis` | 读取既有问题/观察状态和必要概览，不默认联系客户或因重复数据重派分析 |
| 已有完整经营数据，只需要看板 | 总控：`reporting`，复用经营分析中的报告能力 | 渲染和核对上游数据；缺数据补查相应能力，不创造指标或另设报告岗位 |

## 6.9 每次交接的最小任务单与执行约束

以下字段与[委派约定](delegation.md)、[周期协议](operating-cycle.md)、[执行协议](execution-protocol.md)共同使用；本表保留本场景所需的公司资料引用，不另建一套不同的执行流程。

| 任务字段 | 必须交接的内容 |
|---|---|
| 需求与来源 | 用户原始需求、对应问题／J场景编号，来自用户指定还是总控发现；稳定run_id、task_id、issue_id、action_id（如适用） |
| 当前责任与加载 | 路由owner、capability、当前SKILL及完整适用RULES；实际启动时保存agent_id、配置选择或消息显式加载路径；不能用任务名冒充配置自动加载 |
| 对象与期间 | 真实店铺范围、商品／客群／记录引用、买卖身份、统计期间和样本覆盖 |
| 任务模式 | 只读取数／诊断、准备方案、执行已授权变更、核验结果，模式明确 |
| 已有证据与状态 | 后台与公司资料分别引用问题编号、来源、确认时间及版本；当前策略、已有行动/观察状态、实际数据截止时间，标明未知项 |
| 本次目标 | 要回答的问题、预期交付及完成标准；复用已有读取和已完成工作，不重复派工 |
| 动作与授权 | 拟改字段、旧值／新值或内容版本、范围、费用条件及可追溯授权；未定项先准备具体方案，仅补必要决定 |
| 结果返回 | 已确认事实、未证实假设、缺口、交付物／回执、失败和部分完成项；跨领域依赖及触发理由，不能自行启动第二总控 |
| 验收与观察 | 回读责任、指标、固定基线、最早评估时间、样本和数据成熟条件、保护指标、最晚重新审视时间，以及何时保持、干预或重新判断 |

- 分析任务只使用经实时定义确认的查询路径。标题接口可能具备应用动作，方案任务必须明确“只出方案”；`1688_item_title_optimizer_interface` 的名称不能证明它只生成建议。标题来源规则的预估、条件与免责声明完整保留，预估与实测分开标记。
- 同一商品变更只有一个明确执行者。商品运营内部完成诊断、标题/图片方案、已授权应用和回读等阶段；旧名称请求按注册表映射，不把标题方案再派给另一个编辑Agent，也不重复执行用户已经指定的动作。
- 无依赖的只读验证可并行；同一商品、客户或配置的冲突写入串行。重复触发先查已有任务、措施与回执；结果未知先核对后台或原任务，不直接重试。外部已经修改的对象、过期策略或干扰其他观察的方案重新评估。
- 客户跟进和订单接口的时间范围、覆盖渠道和返回类型须核实。模型跟进摘要不是完整原始记录，后台没有记录不能直接认定业务员没有跟进；交付聚合及允许示例，不用调度日志导出全量客户明细。
- 人工审核只处理缺少的具体选择或工具要求的确认；已有授权覆盖的动作继续执行。客户发送、优惠券、报价、接待配置分别判断范围；创建接待、知识入库和非幂等约束不因整合能力而省略。
- 执行前核对实时能力及前置检查。现有广告能力只支持已知诊断；整页详情写回、任意售价修改、报价激活、正式新品发布及ERP写入不能从角色名称推定可用。SKU、阶梯价等销售信息沿用当前后台手动边界，基础属性不替代SKU修改。
- 图片方案、实际生成、上传图片银行、商品应用分别记状态。商品运营复用已有image-agent，不重复让两个角色生成一套；沿用默认imagegen或用户明确选择，不自动切换服务。页面核查仍按6.2独立授权和记录。
- 平台规则仅需核实时加载，竞争比较仅需可比对标时加载，报告能力仅需呈现时加载。采购、发票、售后、分销仅在对应业务目标出现时使用，买卖身份分别核实；客户、库存和履约信号仍可进入经营判断。
- 每个动作先核实执行结果，再按对应场景观察指标复盘；原领域任务可复测，总控汇总并按需核算利润，重要判断可真实启动临时 `operations_review` 复核。配置/文档存在不等于已调用，复核不直接执行业务写入，也不成为常驻第四角色。
- 局部指标改善结合业务结果判断：有效询盘占比提高同时看总量，转人工率下降同时看问题是否正确解决，复制优质商品做法同时看是否分流原商品及利润、库存、履约能否承接。
- 本节不代表已创建每日/周度定时任务或网关拦截。询盘转化状态工具仅提供其 JSON 文件事务锁和请求去重，不覆盖其他记录或业务执行。每次执行须在明确持久位置保存结果，不能只留在聊天；周度策略更新不清零既有措施和基线。

## 6.10 一条具体调用示例（假设场景，不代表本店事实）

输入：“某商品访问增加，但询盘没有相应增加。”

1. 总控先读取该商品既有措施及观察状态，检查G05是否同周期、同口径、实际数据是否更新。已有措施尚未成熟则继续观察；样本小或数据延迟走J02，不自动重复修改。
2. 需要新诊断时，真实委派流量运营检查增长来源，商品运营检查定位、真实条件和已有页面证据；无依赖读取可并行。实际页面优先由用户人工核查，代查前先按6.2取得具体授权，没有结果不得声称“页面已检查”。
3. 增长来自不匹配搜索需求则走J05／J08；仅当证据指向标题时，商品运营在同一任务中进入标题子流程准备方案，根据授权和执行检查应用，不另外启动标题或编辑Agent。
4. 流量匹配但页面缺关键用途／规格则走J09，补公司证据后由商品运营加载图片或属性能力；不需要改主图就不额外生成主图。没有支持的整页详情写接口时交人工应用。
5. 页面准确反映MOQ而目标客户采购量普遍达不到，走J10，由公司决定是否调整供货规则；仅改图片无法解决该条件。
6. 访问质量、页面和交易条件均无充分问题依据时，保存观察或客户反馈待办及重新审视时间，不强制产出一次修改。
7. 实际执行后保存版本、真实回执、后台回读、固定基线、干扰因素及评估条件。总控协调后续复盘；下一轮基于持久状态继续分支，不重新启动整套角色或因仍低于目标再改一次。
