# 固定日报／周报／月报本地呈现

先完成经营分析相应口径的取数、计算和证据整理，再填模板。按[两类分析任务](../../../../references/acquisition-analysis.md#两类分析任务)区别账号整体诊断与投放商品评估，并沿用[销售增长运营流程](../../../../references/sales-growth-workflow.md)。整体成交额仍是经营结果，企业新客、老客和身份未知为明确拆分项；不能用新客表现代替全店结果。正文只展开简短经营结论、优先动作及本轮实际成品，同时在摘要明确给出整体成交额与新老未知拆分。模板渲染出的数值、分母、覆盖及证据详情作为附录或单独详细报表；模板中的填写说明须替换成该店本轮事实，不能原样当业务报告。本流程复用固定本地报告，不替代原报告呈现规则；完整文稿转换等非标准任务仍保留原文必要章节、明细和结论。

- [日报输入模板](../assets/daily-input.json)：`report_type=daily`，`period_basis=single_day_t_plus_1`，起止日必须相同，取数日期至少为该日的次日。数据实际截止时间仍可为统计日当天，例如统计 10 月 27 日、数据截止 10 月 27 日 23:59、取数时间 10 月 28 日 09:00。默认统计日按用户时区取昨日，执行者填写明确日期。
- [周报输入模板](../assets/weekly-input.json)：`report_type=weekly`，`period_basis=independent_period`。默认最近完整周一至周日，主对比前28天对应的完整周，辅比上周；在指标口径中明确各自起止日。显式指定的历史区间仍可填报，不能擅自改成默认窗口。周期数据由支持该区间的来源取得，或按用户明确要求汇总逐日数据，不借用日报接口查询多日。
- [月报输入模板](../assets/monthly-input.json)：`report_type=monthly`，`period_basis=complete_calendar_month`，固定 `Asia/Shanghai`。默认最近已结束的完整自然月，对比前一个完整自然月；保留总量、日均、各自差额和幅度。取数时当月尚未结束不能称为月结；渲染器校验首日、真实月末（含闰年）和取数时间。历史完整月仍可按明确需求填报，月初至今或滚动30天使用长周期分析，不能冒用月报。
- [共用 HTML 框架](../assets/operating-report.html)：固定总览、指标、结论、行动观察、未完成项。版式只在有新的展示需求时调整。

复制输入模板到本轮 `reports/` 目录再填写，保留模板文件。`data_mode=template` 及 `__REQUIRED__` 占位符会被拒绝；只有有真实来源的正式数据才能改为 `actual`。测试数据必须标记 `simulation`，并显式传入 `--allow-simulation`，输出会持续展示“模拟数据，不代表店铺实绩”。该标记仅声明输入性质，渲染成功不能证明输入事实真实。

在项目根目录执行（路径以本轮实际文件为准）：

```sh
python3 scripts/render_operating_report.py --input reports/本轮/daily.json --output reports/本轮/daily.html
```

只依赖 Python 3 标准库，不连接网关或网络，不运行来源中的 Python plan、HTML 或 JavaScript；已存在的输出需要显式 `--overwrite`。输入始终保留。生成后的本地独立 HTML 应打开检查布局，并逐项对照输入及上游证据核验数值；单凭命令成功不能报告视觉核验已通过。

## 字段口径

| 字段 | 填写要求 |
|---|---|
| `period`、`data_cutoff`、`retrieved_at` | 统计区间使用 ISO 日期；两个时间均为带时区的 ISO 时间戳。日报和历史周报保留所声明的用户时区，项目默认 `Asia/Shanghai`，月报固定使用该时区。`data_cutoff` 是数据实际覆盖截止时间，`retrieved_at` 是取得该数据的时间，二者均不是渲染/发布时间；截止时间不得晚于取数时间。日报 T+1 和月报是否已跨月末按取数日期判定 |
| `storeAttribution` | 真实 `store_ref` 和店铺名称；不填凭证。模拟数据用明确的模拟店铺引用 |
| `coverage` | `complete` / `partial` / `unavailable`；后两种须说明缺口，不以零补失败数据。平台数据延迟时可保留早于所选区间结束日的真实截止时间，并明确标为缺失或不可用；不得把这种输入声明为完整数据 |
| `metrics` | 每项保留名称、数值、单位、来源、证据、口径、分母。数值只接收有限数字或 `null`；`null` 必填 `missing_reason`，零值原样显示。比例、净销售额、利润等由上游按其业务规则计算，渲染器不推断、不换算 |
| `findings` | 以 `fact` / `calculation` / `inference` / `recommendation` / `estimate` 区分事实、计算、推断、建议和预估，并引用证据。来源预估规则及免责声明随结论保留，不替代实际观测 |
| `actions` | 保存 `action_id`、对象、状态、负责人、措施说明、证据和下次评估条件。已有观察措施继续沿用原 ID，不凭报告新建或重复执行动作 |
| `unfinished` | 每项说明事项、原因、负责人及下次处理条件；数据缺口、能力限制和实际页面待人工核查均可保留于此 |

没有行动或未完成项时填写空数组；其含义是“本次输入未列出”，渲染器不宣称所有业务已完成。证据支持普通文本或 HTTP(S) 链接；本地路径保留为文本，其他 URL 协议不会生成可点击链接。输入文字全部按文本转义，不能注入脚本。

## 漏斗诊断与经营结果映射

沿用 schema 1 及现有章节，不另造一套报表状态或把缺失数据交给渲染器猜测：

- `metrics` 按全店/核心商品的曝光与点击→访客与新客有效询盘→成熟询盘成交→整体成交及新老未知拆分组织详情。整体成交额及企业新客、企业老客、身份未知成交额全部保留；拆分必须与同范围整体成交额核对，已知覆盖不足不能用估计比例填满。平台归因成交与全店支付成交分别标明，不能相加；平台原值不因业务重分类被改写。身份、成交来源和缺口按[客户身份与成交来源](../../../../references/acquisition-analysis.md#客户身份与成交来源)，已知业务引导老客下单不计广告拉新，身份未知不计已确认新客。
- 整体及本轮核心商品的 `name` 写清“全店”或真实商品ID，`basis` 保留渠道、企业身份核验覆盖、队列及截止；商品级人数不能相加冒充全店去重人数。保留同口径去重访客、新客候选去重访客（可得时）、新客有效询盘客户数及访问到询盘的比率，支持判断“点击足但询盘弱”。新客访客分母不可得时，相应比率保留 `null` 和原因；如以总访客作描述性比较，另列或改用明确名称“新客有效询盘人数/总访客”并写清分母，不能称新客访客转化率，不能把点击次数当访客。询盘条数、客户数、支付订单和买家数分开；直接下单单列，不硬塞进询盘转化。分母与成熟条件按[指标与队列](../../../../references/acquisition-analysis.md#指标与队列)，不可关联时填 `null` 和精确缺项。模板内核心商品行是可复制的结构示例，实际对象由本轮证据或公司目标确定；不适用的示例行可删除并说明范围，不编造商品清单。
- 成交额的新老客队列按共同口径固定在统计期开始前；新客队列期内成交额含首单及后续单，首单人数/金额需要时另列，不能首单后立即切成老客。询盘队列则按询盘发生前的公司成交历史固定新客候选身份；客户后来成交不能反向决定其是否进入询盘分母。两种队列的时点与范围分别写清，不强行对成一条单期漏斗。
- 周/月保留本期及对比期整体销售额、差额和幅度，并在同口径可得时比较身份拆分与漏斗。各行 `basis` 写明真实区间、销售口径及算法，`denominator` 写明幅度分母。对比期为零或未知时，幅度填 `null` 并说明原因，不能写无限增长。月报同时保留两期日均、日均差额及幅度，按各自自然月天数计算；日均不代替整体成交额。周报主比较与上周辅助比较分行并标明。
- `findings` 先写整体经营结果与主要漏斗判断，再给按销售影响、获客证据和实施依赖排序的决定；投放商品优先解释新客获客与成交能力，同时保留全部归因成交及老客贡献。大单、节假日、活动、缺货等已知影响单列，不用大单推定拉新有效，也不删除它对销售的真实贡献。明确事实、计算、待验证假设及关键未知会改变哪个决定；总额差额的算术贡献不等于因果归因。
- `actions` 每个链接单列对象、动作理由、负责人、原 `action_id` 和证据；`description` 关联有证据支持的瓶颈或公司明确的新品/重点推广目标及依据，`next_condition` 写指标、有限观察条件、最晚复查日期及提前干预条件。诊断缺少证据时先补证，不生成泛化改动清单；公司明确要求的新品/重点推广可先准备不依赖缺失数据的方案，不以全店下滑或已有瓶颈结论为前置。
- 长期重点产品由账本 `focus_products` 管理；报告在 `findings` 用事实项呈现 `focus_id`、目标、当前状态、关联行动及下次周/月检查日期。只有真实短期措施进入 `actions` 并沿用各自 `action_id`，不能为了放进报告伪造一个长期行动或用 `focus_id` 冒充行动ID。`unfinished` 保留数据缺口、未具备执行条件的事项与补证时间。报告不把“继续观察”变成无限等待，也不因生成新报告重复执行旧动作。

本地渲染测试位于 `scripts/test_report_rendering.py`：`python3 -m unittest discover -s scripts -p 'test_report_rendering.py'`。模板和渲染程序不创建每日/每周/月度定时任务，不提供业务状态库或执行锁。
