# 询盘与转化分析

这是 `1688-customer-conversion` 内的分析模式，服务于[每日运营与周度检查](../../../../references/operating-cycle.md)。总控做轻量检查、决定优先级和接收摘要；`conversion_analysis` 是按需启动的临时专项，不是第四个核心角色。具体路由以 [task-routing.json](../../../../catalog/task-routing.json) 为准。

按[阶段加载约定](../../../../references/context-loading.md)运行本路由的 `task_context.py`：协调用 `--role director`，实际分析或取数用 `--role executor`。只查看本地状态的轻量监测不加载询盘/CRM业务规则；取询盘数据前加 `--condition inquiry` 并完整读[询盘分析规则](../../../../references/business-rules/1688-inquiry-analyst/RULES.md)，取客户数据前加 `--condition crm` 并完整读[客户管理规则](../../../../references/business-rules/1688-crm-manager/RULES.md)，两者都需要时都加。`conversion_analysis` 按实际范围至少选择一项，所有选中规则的必需来源仍须读取；同上下文同版本可复用，父任务已读不能代替执行者读取。此处只补充持续分析与状态衔接，不改原业务公式或工具条件。

## 每轮先检查，按证据深入

1. 读取当前策略、上一轮监测、同对象问题、既有措施与真实委派状态。首次运行从现有报告和回执核对历史后再建立索引；空索引不是从未处理过。用[状态工具](../../../../references/conversion-state.md)持久化历史核对状态。
2. 获取足够支持轻量判断的新概览：有权限和数据时查看询盘量/质量、接待表现、转人工、客户构成与可取得的成交信号。涉及获客时按[两类分析任务](../../../../references/acquisition-analysis.md#两类分析任务)承接整体及核心商品的新客有效询盘和成熟询盘成交，不以全体询盘或全部归因成交替代。保留整体成交结果及企业新客、老客、身份未知拆分。按经营问题选择必要数据，不把每项工具或所有业务员逐一查询当成每日固定任务。
3. 与相同口径的近期滚动基线、相关措施的行动前固定基线及阶段目标比较。分别输出正常、异常或未知，说明数据截止和覆盖。新数据尚未更新时沿用状态，不能把再次查询当成新发现。
4. 保存规范化观察及证据引用，每轮调用本地状态工具 `ingest`；没有新信号时也传 `signals=[]`，让它扫描全部未结问题及各项措施的复查日期。读取 `outcomes` 和 `due_reviews`，缺席问题不伪造新观察或延后截止时间。工具不替 Agent 判断业务事实或阈值；标准及来源须在输入中明确。
5. 出现符合条件的分析请求时，先确认是否已有相同专项在执行，核对当前策略、授权和问题状态，再 `claim`。待派发后证据或行动改变时，先看最新摘要和证据，通过 `revalidate-request` 留证重核；任务不再适用时用 `cancel-pending` 取消或关联替代策略，不为取消而先启动专员。未知行动先对账。领取成功后按[委派约定](../../../../references/delegation.md)真实启动或恢复 `conversion_analysis`，收到真实任务/Agent ID 后才 `record-dispatch`；已领取、派发或未知不能借 pending 取消绕过恢复。确实无子代理工具时用 `record-direct-start` 登记能力检查依据与代行者，不编造 Agent ID。
6. 专项返回后，总控验收证据、归因和下一步，显式更新问题及措施的观察/复查条件。没有在本次响应里出现的问题不能自动关闭。

每日执行不等于每日修改，也不等于所有指标都有单日接口。原询盘分析在未指定期间时默认最近 7 个已完成日；周期任务已有明确期间时使用实际工具支持的区间，转人工等另有窗口约束。CRM 的累计、近 7 天和近 30 天指标分别保留，不把它们剪裁或改名为昨日数据。日报工具的单日 T+1 限制也不能套到询盘/CRM 工具上。

## 默认只读范围

连接、账号归属和 live Schema 遵循[共用约定](../../../../references/runtime.md)。下表是分析模式的候选读取路径，不是静态可用性承诺；只调用本轮实际所需且实时说明明确为读取的操作。

| 目的 | 候选路径与限制 |
|---|---|
| 团队概览及明确异常的人员详情 | `1688_bp_inquiry_evaluate_summary`；从同周期真实概览匹配身份后才用 `1688_bp_inquiry_evaluate_sales_detail`；不自动下钻全员 |
| 有依据的对话和转人工核验 | `inquiry_data_load`、`query_transfer_inquiries`；索引来自真实结果，保留范围/窗口限制，仅取必要许可样例 |
| 客户量、客群与构成 | `customer_stats`、`customer_list`、`get_customer_profile`；先聚合，筛选人数用服务端总数，主子账号可见范围须记录 |
| 明确对象的已有跟进/订单证据 | `get_followup_record_by_buyer`、`get_order_info_by_buyer`；记录覆盖渠道、周期及原始记录/模型摘要区别，不据摘要证明逐条消息送达 |
| 已有单客画像 | `customer_ai_profile` 只有经 live Schema 确认的 `action=query` 可用；`refresh`、更新、生成均不属于本分析范围 |
| 已有系统计划和状态 | `newton_ai_crm_plan_operation` 只有 `operation=query`；需该证据时再读[原触达规则](../../../../references/business-rules/1688-outreach-operator/RULES.md)及[查询适配](crm-query.md) |

不把 `customer_ai_profile` 或包含查询功能的混合工具整体标为只读。无法确认某操作是否产生副作用时，先取得说明，仍不明确则记录该项能力缺口，使用可完成的读取结果继续分析。

本模式不执行客户导入、标签或属性写入、画像刷新、接待配置、知识入库、报价变更、计划创建/启停、发券、客户消息或内部跟进提醒。用户单独明确要求这些工作时，继续使用同一技能中的原维护、接待、报价、触达模块及对应业务前置；不因新增分析层删除原能力。分析结论只能形成建议，不能自动授权商业承诺或销售动作。

本地脚本不联网、不调用业务工具；角色说明和实时操作核对约束执行行为，不能阻止宿主另行直接调用其他工具。只有真实网关提供并验证了限制，才能称为硬权限隔离。

## 证据与可比性

每项判断保留店铺引用、对象、实际统计期间、数据截止、查询时间、来源和版本、指标定义、单位/分母、去重方式、样本量、数据覆盖及证据路径。基线的区间和定义单独存储；时间区间、渠道、买家阶段或统计单位不一致时，不直接计算转化差异。

- 企业新客、老客及身份未知依[客户身份与成交来源](../../../../references/acquisition-analysis.md#客户身份与成交来源)核验，身份与广告获客来源分别判断。企业新客是对本公司新成交客户；平台首购、CRM建档时间、空订单字段不能证明，已有未成交线索也不能自动归老客。保留核验时点、历史覆盖和证据冲突；企业身份未知与来源未知分别披露，不用平台标签改写企业结论。
- 新客有效询盘的成交前队列、有效性和去重定义依[指标与队列](../../../../references/acquisition-analysis.md#指标与队列)；不能只将后来成交者放进分母。平台询盘、平台优质询盘保留原名，有效性缺少证据时记待核，不将其自动当作新客有效询盘。账号整体与核心商品分别观察，同一客户跨商品不能直接相加去重。
- 询盘条数、询盘客户数、订单数、成单客户数分别统计；比例分子和分母必须属于可关联的同一队列与观察范围。系统高意向计划覆盖人数不等于全库高意愿客户人数。
- 新发生询盘与既有成熟询盘分别观察，“新发生”不等于企业新客。只有线索年龄、采购周期、样本及成交回补条件达到有依据的评估条件，才评价同批有效询盘的成交；不能以本期全部订单除以本期询盘。直接下单与询盘后成交单列，跨期订单回到原队列；成熟条件来自已知业务周期/历史证据/来源规则，不机械规定所有商品等 7 天。清楚的接待事实错误可独立处理，不必等待成交成熟。
- 报价、寄样、回访、履约是否超过已确认承诺时间，属于过程事实。按状态契约单列 `process_commitment`，保存承诺来源、具体动作、到期时间、实际证据覆盖时点及 fulfilled/missed/unknown/not_due，使用 `maturity=not_applicable`。有据且已到期的过程异常及时分析，不等成交周期；没有记录或站外不可见仍为未知。旧 followup/order 等结果指标仍受成熟度限制，不能只改成熟度枚举绕过。承诺期限或内容变更留理由和证据，原超时事实保留；事后补做完成不等于原承诺准时兑现。
- 没有跟进、报价、寄样或线下订单记录可能是接口不可见、记录未录入或窗口不覆盖，标为未知；不能写成“销售未跟进”“客户没有报价”“未成交”。没有真实采购意愿评估也不是低意愿。
- 不同渠道、采购目的、起订量、客单价和新老客结构可能改变结果。先核对可比范围；关联或前后变化只支持假设，不能直接证明流量、商品或销售是唯一原因。
- 明细只是许可样例时，只能说明样例中出现的情况，不能外推全店比例。缺失或回补数据形成证据缺口，不能自行填零、臆测原因或用来源预测替代观测。

## 持续问题、观察与复查

采用[本地状态契约](../../../../references/conversion-state.md)；不要另建第二套问题 ID、客户主档或在聊天中另存状态。问题身份依据店铺、稳定对象、问题类型及稳定的队列/指标定义，查询日期和文件路径变化本身不产生新问题。新客队列使用现有 `cohort_id/metric_id` 和证据引用，口径变化留版本及与旧基线的关系，不覆盖旧结论或把身份核验结果扩为CRM写入。

| 当前情况 | 本轮处理 |
|---|---|
| 新的有依据异常，或足以改变结论的新事实 | 建立/更新同一问题，按阈值依据和证据提出专项分析请求 |
| 同一异常仍在，已有一项或多项措施执行/观察中 | 按 action_id 分别保留状态、固定基线和复查日期；一项完成不覆盖其他项，任一未知先对账；不重复派发同一调整，不生成每日销售催办 |
| 数据未更新、重复读取或仅查询时间变化 | 保留既有状态；不算重要新证据、不重复创建专项 |
| 到达问题或某项措施复查条件 | 即使本轮商品缺席或无新信号，也由全量到期扫描提出一次请求；同问题多个到期条件合并，仍在执行或结果未知先核对实际任务，不每日重派 |
| 有新的可靠事实或达到既定提前干预条件 | 记录条件、证据及对原措施的影响，由总控决定提前复查，不以“仍低于目标”替代条件 |
| 样本未成熟或数据不完整 | 记观察/证据缺口，给出下一次可判定条件；到最晚复查点重新决定，不能无限等待或自动判失败 |
| 本次未取到该对象、数据源缺失或看不到旧问题 | 保留原问题；缺席不等于恢复正常 |
| 已有足够证据支持结论或恢复 | 总控显式验收并记录结论、证据及后续观察；所有关联措施逐项处理，未知/观察中措施不能随问题结案消失；不能凭一条正常信号静默清空历史 |
| 待派发分析被新策略替代或已无必要 | 仅对 pending 取消/标记替代并留证，不伪造分析完成；业务问题保留复查安排，已领取或在途任务走原对账恢复路径 |

重要新证据指事实、统计内容、实际截止、覆盖或定义等发生与判断有关的变化。单纯查询时间、报告路径、重复描述或重新生成摘要不构成重要新证据。阈值、最早评估时间、最晚复查时间及提前干预条件使用策略或有依据的本轮判断，记录来源；不得为制造任务每天调整阈值。

状态工具产生的 `request` 只是待调度请求。启动前与实际任务状态核对，启动回执与结果分别登记；任务超时/未知不能直接重派。schema 2 将同问题多项措施按ID保存，兼容schema 1的首次事务迁移会保留原快照、回执和问题/请求标识；迁移提示需对账的历史措施或旧pending不能直接跳过。状态锁只保护该文件更新，不覆盖模型、网关或其他经营状态，也不把队列变成调度服务。外部公司策略变化由总控核对，本地散列不能自动识别尚未录入的决定。

## 专项交付与总控分流

专项只读取交接所需的问题、摘要、有限证据和原规则，不接管整店。正文返回简明经营结论、排序后的决定、已有授权范围内完成的产物及下一责任方；结论保留整体成交与新老未知拆分、相关新客询盘队列的覆盖及成熟度。附录或证据引用承载事实/计算/推断、稳定问题 ID、已有措施及观察条件、需补事实及下次复查条件，不返回整库客户或完整对话档案。没有关键身份或来源证据时，说明它具体阻塞哪个判断，继续完成不依赖它的分析与准备。

| 有依据的发现 | 总控后续处理 |
|---|---|
| 需求与进店流量不匹配、来源结构变化 | 交 `traffic_operations` 做渠道/投流分析；写入仍须核验能力和具体授权 |
| 商品真实信息、规格、MOQ 或页面承诺导致疑问 | 交 `product_operations` 核对事实与适用修改；销售 SKU/阶梯价格及实际页面核查仍遵循现有边界 |
| 明确的响应、交接或跟进流程问题 | 记录给销售/责任人的具体建议及证据，由总控纳入事项；默认不发送提醒、不直接联系客户 |
| 报价政策、交期、产能、利润或商业条款决策 | 记录待企业负责人决定的具体事实与选项，不替企业承诺 |
| 新线索或样本未成熟 | 保持观察，列明成熟与复查条件 |
| 来源不全、口径混杂或只能提出多种原因 | 待查/证据缺口；列最小补证路径，不强行归责 |

总控把已授权且明确可执行的商品/流量事项纳入现有行动记录并按领域委派；本专项不直接写商品、投放或客户数据。多种原因可并存，用同一问题的 `related_actions` 关联不同措施，各自保存观察和复查；每次只更新所列ID，不能用新措施替换整个行动集合。验收时已到期的未完成措施须逐项给出结论或新复查日，不能只延后问题总日期。没有新增可执行事项时仅更新状态，只有影响具体决定且现有工具无法补齐的事实才提交用户事项；不要求用户每天手工补录全链路数据。

## 隐私和留档

汇总为主，所有报告、状态、日志和交接合计只保存本任务必要的最多 20 条许可示例，不全量导出、不分页拼接绕过限制。站内手机号隐藏，不按省/市/区筛选、展示、分析或分组；原工具目录含地域工具也不构成例外。状态不保存客户画像原文、无关对话和认证信息。

`LOGINID_..._LOGINID` 只在确需调用或交接时按原包装内部传递，用户报告用脱敏别名；普通问题键采用聚合对象或脱敏标识，不包含身份凭证。保留证据所需最小信息与访问位置，来源不支持的完整客户数据不为“以后方便分析”而额外落盘。
